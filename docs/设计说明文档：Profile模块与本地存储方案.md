# 一、用 Profile 替代传统 User 模块的原因

> **当前扩展：** Profile 除基础参数、统计偏好和工具链配置外，也作为会话、
> 任务、专属 RAG 知识和长期记忆的隔离边界。详见
> [RAG 与长期记忆](./RAG与长期记忆.md)。

## 1. 项目定位：不需要“用户账户”

本项目的本质是一个**开源、自托管的音乐改编工具**，而非面向公众的 SaaS 服务。绝大多数使用场景是：开发者或用户在自己电脑上（或 GitHub Codespaces 等个人可控环境）运行后端，然后通过浏览器使用。在这种模式下：

- 不存在多租户隔离需求，实际只有“当前使用者”一人。
- 不需要注册、登录、密码找回、邮箱验证等复杂流程。
- 不需要跨设备同步数据，用户的数据完全属于其当前运行环境。

传统 User 模块（带用户名、密码、邮箱等）会引入不必要的复杂性和法律合规负担（个人信息保护法要求对敏感字段进行保护），而这与本项目的特性相悖。

## 2. Profile 更贴合“个性化配置管理”的真实需求

用户真正需要的功能是：

- 记住自己常用的乐器偏好（例如“我喜欢钢琴”），记住自己讨厌的音色（例如“我不喜欢大提琴”）。即记忆用户音乐偏好。
- 记住自己常用的铃声时长、速度等默认参数。
- 可以清空、重置、导出这些配置。
- 可以在不同配置之间切换。

这些需求本质上属于**个人偏好（Profile）**，而不是“账户（Account）”。Profile 不需要密码，不需要唯一标识跨会话，也不需要与任何第三方身份绑定。它只是本地存储的一份配置。

## 3. 法律与合规优势

- 传统 User 表会包含 `username`、`password_hash`（如果实现登录）等敏感信息。根据《个人信息保护法》，一旦收集这些信息，项目维护者就需要承担数据保护义务，包括数据加密、泄露通知、用户权利响应等。即使项目只是开源代码，一旦有公共部署实例，这些义务就不可避免。
- Profile 方案中，**所有配置数据完全存储在用户的浏览器存储或本地存储中**。项目作为纯开源工具存在。

## 4. 简化部署与维护

- 无需处理密码重置、会话过期、JWT 续期等逻辑。
- 无需担心数据库中的用户表被暴力破解或泄露。
- 依然能够保证用户之间不会相互干扰（即使多人共用同一台机器，也可以各自使用不同Profile）。

# 二、继续使用本地文件存储（而非 OSS / 对象存储）的原因

## 1. 项目性质决定“无中心化存储”是最安全的设计

- 项目不是商业产品，没有预算和运维团队来维护一个可靠的对象存储服务（如 AWS S3、阿里云 OSS）。
- 一旦引入 OSS，就意味着项目维护方需要承担**存储费用、密钥管理、数据合规**等责任。用户上传的音频可能是受版权保护的内容，存储到云上会带来法律风险（侵权内容存储责任）。
- 本地存储（`uploads/` 和 `static/ringtones/` 目录）完全由用户自己控制。用户对自己的数据拥有完整的物理控制权，可以随时删除、备份、审计。

## 2.音乐改编带来的版权风险

我们的工具提供可以对用户上传的音频（未来可能提供直接搜索功能）进行改编的服务，如果用户只是自己使用改编的铃声当然不会面临法律问题，但如果在公开场合进行传播是有极高的侵权风险的。从这个角度考虑，我们一方面需要在公开项目前加入免责申明，另一方面不应该实际存储用户上传的音频和最终结果的数据。
