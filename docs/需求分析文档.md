
# RingTurn 需求分析文档

> 项目定位：南京大学 2026 春季学期《软工三》课程项目，展示 AI Agent 的规划/决策/反思与全栈工程化。
>
> **文档状态：需求基线。** 本文描述目标和验收语义，不保证所有内部实现细节
> 与当前代码一致。已落地架构和运行边界见 [根 README](../README.md) 与
> [Agent 详细设计](./Agent详细设计.md)。

## 1. 背景与目标
### 1.1 背景
用户希望将喜欢的音乐片段改编为“可用于手机铃声的纯音乐”，传统流程需要掌握编曲、MIDI、音色与渲染工具，门槛高、迭代成本大。

### 1.2 目标
- 用户仅需：上传音频 + 自然语言描述目标风格/约束，即可生成个性化 MP3 铃声。
- Agent 能在一次生成后，根据用户反馈进行多轮迭代，并“记住”偏好与修改意见。
- 系统强调：可解释的规划步骤、可观测的执行过程、可复现的中间产物（旋律/和弦/MIDI/渲染参数）。

### 1.3 非目标
- 不提供商业版权音乐分发/变现能力。
- 不承诺对受版权保护的内容进行规避或合法性判定（仅做项目级提示与约束声明）。
- 不追求专业录音棚级音质与人类编曲师同等效果；以“可用铃声”和可迭代为核心。

## 2. 相关方与用户画像
### 2.1 相关方
- 终端用户：上传音频并提出改编需求，反复调整直到满意。
- 项目开发者：实现前后端、工具网关与 Agent 工作流，保证可演示、可复现。

### 2.2 用户画像与典型场景

本系统的核心用户通常不具备编曲/MIDI/音色渲染经验，但希望用“自然语言 + 少量反馈”获得可用铃声；少部分用户会进行多轮精调，并关注版本对比与可复现性。

#### 画像（Persona）
- 用户 A（普通学生 / 结果导向型）
	- 目标：快速得到一个“像某种风格”的纯音乐铃声（例如温柔钢琴），用于日常来电。
	- 痛点：不知道“该怎么描述参数”；无法判断该截取哪一段；不想等待太久。
	- 成功标准：一次或少量轮次内得到“听起来舒服、时长合适、不突兀”的 MP3。

- 用户 B（重度折腾 / 迭代优化型）
	- 目标：通过多轮反馈把作品“磨到满意”，例如控制鼓点强弱、结尾处理、调式/速度变化等。
	- 痛点：每一轮到底改了什么不清楚；担心越改越偏；希望能回退或对比版本差异（至少能区分版本与生成参数摘要）。
	- 成功标准：系统能稳定记住偏好与历史尝试，反馈能在下一版结果中体现。

- 用户 C（轻度音乐爱好者 / 可控性需求型）
	- 目标：希望系统在自动化的同时，能接受更明确的约束（如“不要弦乐”“节奏更平”“更短一点”）。
	- 痛点：自动化改编可能产生不符合预期的音色/段落选择；对“过于机械/过于吵”的结果不满意。
	- 成功标准：Agent 能把约束落实到计划里，并在结果摘要中体现关键参数。

#### 典型场景（Scenario）
- 场景 S1：一次性生成
	- 用户上传 10–60 秒音频并输入“风格 + 时长”描述。
	- Agent 直接执行分析→MIDI→改编→截取→渲染→质检，输出可试听/下载的铃声。
	- 体现点：端到端闭环、阶段进度可见、输出参数摘要。

- 场景 S2：用户反馈驱动的多轮迭代
	- 第 1 版生成后，用户反馈“鼓点太强、结尾太突然”。
	- Agent 将反馈映射为可执行修改（减弱节奏/鼓点、增加淡出或重新截取/收尾处理），生成第 2 版。
	- 体现点：记忆模块保存偏好与已尝试方案；反思器调整计划并解释修改方向。

- 场景 S3：外部工具失败与恢复
	- 分析或渲染工具在某次调用失败（超时、输入异常）。
	- 系统能明确告知失败阶段与原因，并提供可操作建议（换片段/换格式/稍后重试），必要时使用 Mock 工具保障演示闭环。
	- 体现点：Tool Gateway 统一封装与降级策略；任务不会“无响应”。

- 场景 S4：偏好复用
	- 用户历史上多次选择“钢琴、不要大提琴”。
	- 新任务中 Agent 默认沿用偏好，除非用户显式修改。
	- 体现点：偏好持久化与默认参数策略让交互更省心。

## 3. 系统范围与边界
### 3.1 系统边界
系统包含：Web 前端交互、后端 API、Agent 核心（规划/执行/记忆/反思）、外部工具调用网关、文件存储与数据库。

系统不包含：商业音乐库版权审核、付费音源接入、复杂社交分享生态。

### 3.2 输入与输出
- 输入：本地音频文件（MP3/WAV）与自然语言改编描述。
- 输出：可下载/播放的铃声音频（优先 MP3），并保留中间产物（如 MIDI）用于复现与迭代。

## 4. 总体业务流程（用户视角）
1. 用户上传音频。
2. 用户用自然语言描述目标风格与约束。
3. Agent 解析需求。
4. Agent 执行流水线：音乐分析 → 主旋律/和弦提取 → MIDI 生成 → 改编（音色/节奏/调式/截取） → 渲染输出 → 质检。
5. 用户试听结果并给出反馈。
6. Agent 记忆反馈并反思，重新规划与生成新版本。

## 5. 功能性需求
以下需求以“必须（MUST）/应该（SHOULD）/可以（MAY）”标注优先级。

### 5.1 音频输入与管理
**FR-1 上传音频（MUST）**
- 用户可上传本地音频文件，支持 MP3/WAV。
- 系统应校验文件类型与大小；校验失败返回可理解的错误信息。
- 上传成功后生成可引用的音频资源 ID，并记录文件存储路径与元数据（时长、采样率可选）。

### 5.2 需求理解与对话澄清
**FR-2 自然语言需求输入（MUST）**
- 用户可输入改编目标描述（示例："温柔钢琴风"、"清晨阳光般的铃声"）。

**FR-3 需求解析与参数化（MUST）**
- Agent 应将描述转化为可执行参数集合，至少包含：
	- 乐器/音色倾向（钢琴/吉他/弦乐等）
	- 情绪/强度（柔和/明亮/沉稳等）
	- 目标时长（默认给出合理值，或询问用户）
	- 节奏/鼓点强度（默认中性，或从文本推断）
- 当关键参数缺失且无法可靠推断时，Agent 应发起澄清提问。

**FR-4 多轮对话迭代（MUST）**
- 用户可针对结果提出修改意见（如“鼓点太强”“结尾太突然”“更短一点”）。
- Agent 必须将反馈转化为对下一轮计划的约束/修改，并生成新版本。

### 5.3 任务编排与进度可见
**FR-5 任务创建与状态管理（MUST）**
- 每次生成/迭代应创建一个任务或版本，包含状态：排队/进行中/成功/失败。
- 任务必须可查询当前阶段（分析/生成MIDI/改编/渲染/质检）与错误原因（失败时）。

**FR-6 过程产物记录（SHOULD）**
- 系统应记录关键中间产物的引用（如：旋律/和弦结果摘要、MIDI 文件路径、渲染参数）。

### 5.4 音乐分析与 MIDI 生成
**FR-7 音乐分析（MUST）**
- 系统应对输入音频进行结构与音乐要素分析，至少支持：主旋律与和弦的提取（可简化）。
- 当分析失败（噪声过大/文件损坏）时，应返回可操作的失败原因与建议（如更换片段/换格式）。

**FR-8 MIDI 生成（MUST）**
- 系统应基于分析结果生成原始 MIDI 作为中间表示。
- MIDI 需要可被后续改编与渲染步骤使用。

### 5.5 改编与智能截取
**FR-9 乐器/音色改编（MUST）**
- 系统应根据需求选择或替换乐器音色（至少覆盖：钢琴、小提琴）。

**FR-10 其他改编操作（SHOULD）**
- 支持根据需求进行升/降调、改变节奏（可为有限集合的操作）。

**FR-11 智能截取（MUST）**
- 系统应输出适合作为铃声的片段：
	- 可自动选择“最合适段落”（例如副歌/主题最明显处）。
	- 若用户指定时长，应尽量满足该时长（允许小幅偏差并说明）。

### 5.6 渲染输出与交付
**FR-12 渲染输出音频（MUST）**
- 系统应将改编后的 MIDI 渲染为音频文件，输出格式优先 MP3（可内部先 WAV 再转码）。

**FR-13 下载（MUST）**
- 用户能够下载最终铃声文件。
- 系统应提供生成结果的基本信息：时长、版本号/生成时间、使用的风格/关键参数摘要。

### 5.7 质量评估与反思
**FR-14 自动质检（SHOULD）**
- 系统应对渲染结果做自动检查，至少覆盖：
	- 时长是否符合目标
	- 结尾是否过于突兀（可用能量/包络启发式）
	- 音量是否过小/过大（可选）
- 质检失败时：
	- 可直接判为失败并给出原因，或
	- 触发 Agent 反思并自动重试一次（重试次数需可配置）。

**FR-15 反思驱动的重规划（SHOULD）**
- 当质检不通过或用户反馈强烈时，Agent 应调整下一轮计划（例如改用更柔和的音色、增加淡出、重新截取段落）。

### 5.8 记忆与偏好
**FR-16 会话记忆（MUST）**
- Agent 必须在会话内保留：用户偏好、已尝试方案摘要、最近一次产物引用，确保多轮迭代“前后一致”。

**FR-17 偏好持久化（SHOULD）**
- 系统应在数据库中存储可复用偏好（如“不喜欢大提琴”“更偏好钢琴”），用于后续任务默认参数。

## 6. 非功能性需求
### 6.1 性能与容量
- **NFR-1（SHOULD）** 对常见长度（例如 10–60 秒）的输入，单次生成应在可接受时间内完成；若耗时较长，应提供进度反馈。
- **NFR-2（MUST）** 处理大文件时应有上限与超时机制，避免阻塞服务。

### 6.2 可靠性与容错
- **NFR-3（MUST）** 外部工具失败时应可定位（记录阶段与错误）、可恢复（允许重试或返回可操作建议）。
- **NFR-4（SHOULD）** 任务应支持幂等查询：用户刷新页面不应丢失任务状态。

### 6.3 可用性
- **NFR-5（MUST）** 关键交互（上传、提交需求、查看进度、试听下载、反馈修改）应在少量步骤内完成。
- **NFR-6（SHOULD）** Agent 的澄清问题应尽量简短明确，避免一次性询问过多信息。

### 6.4 安全与隐私
- **NFR-7（MUST）** 上传文件与生成产物应有访问控制（至少做到“不可被随机枚举的 URL/ID”）。
- **NFR-8（SHOULD）** 对临时文件设置过期清理策略（可配置）。

### 6.5 可维护性与可观测性
- **NFR-9（MUST）** 记录结构化日志：任务ID、阶段、耗时、失败原因，便于演示与排障。
- **NFR-10（SHOULD）** Agent 决策应可追溯（保存计划摘要与关键参数）。

## 7. 风险与应对
- 风险：音频分析在某些歌曲上效果差 → 应对：引导用户换更清晰片段；提供“重新截取/重新分析”重试。
- 风险：渲染耗时长 → 应对：任务异步化 + 进度可见；限制输入长度/文件大小。
- 风险：外部工具不可用 → 应对：Tool Gateway + Mock；对失败做降级与提示。
